# פרויקט Supabase משותף — דוביד ואופסיידס

> **התשובה: כן.** פרויקט אחד, חשבון אחד למשתמש, הפרדה מלאה בין
> המוצרים. זה בדיוק מה ש-PostgreSQL schemas נועדו לו.

## המבנה

```
פרויקט Supabase אחד
│
├── auth.users        ← זהות משותפת. חשבון אחד, שתי אפליקציות.
│
├── public.*          ← אופסיידס   arenas · bets · matches · profiles
├── core.*            ← משותף      teams · players · fixtures · match_events
├── game.*            ← דוביד      lineups · scores · leagues
└── shared.*          ← הגשר       reward_grants  (וזהו)
```

`core` משותף כי עובדות כדורגל הן עובדות: אין סיבה ששני המוצרים
יחזיקו שתי רשימות שחקנים שיתפצלו בעוד חודשיים.

`shared` מכיל **טבלה אחת בלבד**. ברגע שהוא יגדל, הוא יהפוך לצימוד.

## ההפרדה — ארבע שכבות בלתי תלויות

| # | שכבה | מה היא מונעת |
|---|---|---|
| 1 | **Schemas** | `game.leagues` ו-`public.arenas` לא יכולים להתנגש. שמות זהים חיים זה לצד זה. |
| 2 | **Exposed schemas** | PostgREST חושף רק מה שברשימה. סכימה שלא נחשפה לא קיימת מבחוץ. |
| 3 | **`db.schema` בקליינט** | הקליינט של דוביד מכוון ל-`game`. הוא *לא רואה* את `public` בלי לבקש במפורש. |
| 4 | **RLS** | גם אם 1–3 נכשלו, השורה עדיין מוגנת. |

הנקודה: אף אחת מהן לא מספיקה לבדה, וכולן יחד אומרות שדליפה
דורשת ארבע טעויות בו-זמנית ולא אחת.

## הקוד

**קליינט דוביד:**
```ts
export const supabase = createClient(URL, ANON_KEY, {
  db: { schema: 'game' },        // ← ברירת המחדל של כל שאילתה
});

// דאטת כדורגל משותפת — בקשה מפורשת, ולכן גלויה בקוד
const players = await supabase.schema('core').from('players').select('*');
```

**קליינט אופסיידס:** לא משתנה בכלל. הוא ממשיך על `public`.

**הגדרות:** Dashboard → Settings → API → Exposed schemas →
`public, core, game, shared`

**הרשאות:** רצות אוטומטית במיגרציה `db/07_shared_supabase.sql`.

## זהות

```
auth.users.id ──┬── public.profiles   (אופסיידס: יתרה, 💨, אווטאר)
                └── game.users        (דוביד: שם תצוגה, העדפות)
```

אותו אדם, שני פרופילים, אפס צימוד. אופסיידס יכול לשנות את מבנה
הפרופיל שלו מחר בלי לגעת בדוביד, ולהפך.

`game.ensure_profile()` יוצר פרופיל דוביד בכניסה ראשונה — בלי מסך
הרשמה נוסף. מי שכבר רשום באופסיידס פשוט נכנס.

## פרסים חוצי־אפליקציות

```
דוביד: ניצחת מחזור
   ↓  shared.grant_reward(... idempotency_key: 'dubid:gw7:win:<user>')
shared.reward_grants  status=pending
   ↓  אופסיידס קורא את הממתינים
אופסיידס מזכה 200 💨 → shared.claim_reward(id) → status=claimed
```

שלוש הגנות, כולן במסד ולא ב"נזהר בקוד":

1. **`idempotency_key` UNIQUE** — הענקה כפולה בלתי אפשרית. `cron`
   שרץ פעמיים מקבל את אותה שורה, לא שתיים.
2. **`claim_reward` נועל שורה** (`FOR UPDATE`) ודוחה מימוש שני.
3. **`grant_reward` לא ניתן ל-`authenticated`** — רק `service_role`.
   בלי זה כל לקוח היה מעניק לעצמו פרסים.

## ★ מה שאני חייב לומר לפני שתחליט

פרויקט אחד הוא **רדיוס פגיעה אחד**:

- מיגרציה גרועה בדוביד יכולה להפיל את אופסיידס.
- מיצוי ה-connection pool באפליקציה אחת מרעיב את השנייה.
- שחזור מגיבוי הוא הכול-או-כלום. אי אפשר לשחזר רק את דוביד
  ליום שלישי ולהשאיר את אופסיידס בהווה.
- אופסיידס יושב על `public`, שהוא ברירת המחדל של PostgREST.
  צריך לוודא ש-`db.schema` מוגדר בקליינט של דוביד, אחרת שאילתה
  בלי `.schema()` תפגע ב-`public` בטעות.

**המלצתי: לך על זה בכל זאת**, כי הזהות המשותפת והפרסים חוצי־
האפליקציות שביקשת דורשים `auth.users` אחד — ושני פרויקטים היו
מחייבים סנכרון משתמשים, שהוא בעיה קשה בהרבה מהסיכונים למעלה.

אבל שני דברים חייבים לקרות לפני:

1. **מיגרציות ממוספרות ומסודרות לשני המוצרים.** לאופסיידס יש
   היום 272 קובצי `patch-*.sql` שמורצים ידנית. זה עבד כשהוא היה
   לבד; עם דוביד באותו מסד זה הופך לסיכון ממשי.
2. **סביבת staging.** אין דרך לבדוק מיגרציה משותפת על פרודקשן.
