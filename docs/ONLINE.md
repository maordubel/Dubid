# הכל און ליין — מה השתנה ומה להריץ

## 1. הבעיה, בשורה אחת

לוח הניהול **כתב** למסד. אף מסך לא **קרא** ממנו.

14 הקבוצות ו‑351 השחקנים חיו בקובץ `src/data/squads.ts` — קוד
TypeScript שנארז לתוך ה‑JavaScript בזמן בנייה. לוח המשחקים חי
ב‑`src/data/fixtures.ts`. אז כשהזנת מחיר חדש:

1. הפונקציה במסד רצה. ✓
2. השורה השתנתה. ✓
3. `game.audit_logs` תיעד. ✓
4. המסך המשיך להציג את המספר מהקובץ. ✗

זה נראה בדיוק כמו "האדמין לא שומר". הוא שמר.

---

## 2. מה עבר לשרת

| מה | איפה זה היה | איפה זה עכשיו |
|---|---|---|
| קבוצות ושחקנים | `src/data/squads.ts` | `game.squads()` |
| לוח משחקים | `src/data/fixtures.ts` | `game.fixtures('gw-2')` |
| דדליין וסטטוס מחזור | חושב בדפדפן | `game.gameweeks` |
| טיוטת הרכב | `localStorage` | `game.lineup_drafts` |
| שם התצוגה | `localStorage` | `game.users.display_name` |
| מטמון הגשות ותוצאות | `localStorage` | *הוסר* |
| מטמון זירות | `localStorage` | *הוסר* |

**מה נשאר במכשיר, ואין ברירה:** סשן ההזדהות של Supabase
(`sb-*`). הוא לא נתון של המשחק — הוא המפתח שמוכיח מי אתה מול
השרת, כמו עוגיית התחברות בכל אתר. בלעדיו כל רענון היה יוצר
משתמש חדש.

*(נשארו גם שני זיכרונות תצוגה זעירים: איזו פרסומת נסגרה ואיזו
הצעת הרשמה נדחתה. הם לא נתוני משחק, ואף אחד לא מתחרה עליהם.)*

---

## 3. איך שינוי מגיע לכל המכשירים

טבלה אחת, `game.data_revision`, מחזיקה מספר אחד. טריגר על כל
טבלת דאטה מעלה אותו בכל שינוי — **פעם אחת לפעולה**, לא פעם
לכל שורה.

```
אדמין משנה מחיר
   → core.squads מתעדכן
   → הטריגר מעלה את המונה
   → Realtime משדר
   → כל מכשיר שפתוח מושך מחדש את game.squads()
   → המחיר החדש על המסך, בלי רענון
```

בלי זה, "און ליין" היה אומר "נכון לרגע שבו טענת את הדף".

## 4. מה להריץ — שלושה שלבים

### שלב 1 · המסד

Supabase → SQL Editor → הדבק והרץ:

```
db/RUN-ALL.sql
```

הקובץ מכיל את כל 12 המיגרציות לפי הסדר, כולל החדשה. הוא
**אידמפוטנטי** — אפשר להריץ אותו שוב, ושוב, ובכל סדר. אם כבר
הרצת את הקודמות, אפשר להריץ רק את `db/13_live_data.sql`.

**בדיקה שזה עבד** — הרץ ב‑SQL Editor:

```sql
SELECT * FROM game.v_live_health;
```

הציפייה:

| עמודה | ערך תקין |
|---|---|
| `mapped_teams` | 14 |
| `active_players` | 351 |
| `players_without_price` | **0** |
| `players_without_tier` | **0** |
| `teams_without_short` | **0** |
| `matches` | 7 |
| `revision` | מספר כלשהו > 1 |

אם `players_without_price` גדול מ‑0 — הסיד לא רץ. הרץ
`db/03_seed_squads.sql`.

### שלב 2 · Realtime

Supabase → Database → Replication → `supabase_realtime`

ודא ש‑**`game.data_revision`** מסומנת. המיגרציה מוסיפה אותה
אוטומטית; אם היא לא שם, סמן ידנית.

בלי זה הכל עובד חוץ מדבר אחד: שינוי אצלך לא קופץ למסכים
שפתוחים אצל אחרים. הם יראו אותו ברענון הבא.

### שלב 3 · הפרונט

```bash
npm install
npm run build
```

ואז פרוס ל‑Vercel כרגיל.

> **חובה לבנות מחדש.** הפעם זה לא "מומלץ": `src/lib/liveData.ts`
> הוא קובץ חדש, ובלי בנייה הדפדפן ממשיך להריץ את הגרסה שקוראת
> מהקובץ הסטטי — כלומר בדיוק המצב שתוקן.

## 5. בדיקה שהכל באמת מקוון

היכנס ללוח הניהול → לשונית **מערכת**. שבע בדיקות:

| בדיקה | מה היא אומרת |
|---|---|
| זהות | כניסת אורח פועלת |
| מסד · סכימה ומיגרציות | המיגרציות רצו |
| **דאטת כדורגל מהשרת** | `game.squads()` עונה — עם מספר קבוצות ושחקנים |
| **טיוטות בשרת** | ההרכב שבבנייה עובר בין מכשירים |
| תוצאות ונתוני מחזור | `game.results()` עונה |
| שעון השרת | ההפרש מהמכשיר קטן |
| הרשאת ניהול | אתה אדמין |

בתחתית לשונית **תוצאות** מופיע גם:

```
קבוצות בליגה: 14 · שחקנים בסגלים: 351 · מהשרת
```

אם כתוב **"מהקובץ המקומי — אין חיבור"** באדום, המסך עדיין מציג
את הזרע הסטטי. אז שלב 1 או 2 לא הושלמו.

## 6. המבחן האמיתי — לשחק עם חברים

1. פתח את האתר בטלפון. בנה הרכב חלקי. **אל תגיש.**
2. פתח את אותו אתר במחשב, באותו חשבון.
   → ההרכב החלקי צריך להיות שם.
3. שלח את הקישור לשלושה חברים. שכל אחד יגיש.
4. פתח את הדירוג בכל המכשירים.
   → אותה טבלה, אותו סדר, אצל כולם.
5. בלוח הניהול שנה מחיר של שחקן.
   → המחיר משתנה במסכים הפתוחים **בלי רענון**.
6. הזן תוצאות ולחץ **פרסם דירוג**.
   → הניקוד קופץ אצל כולם.

השלב היחיד שלא נבדק כאן הוא משיכת נתונים מ‑API‑Football — הוא
עדיין לא מחובר, לפי בקשתך.

## 7. לשונית "מחזור" — חדשה

עד עכשיו הדדליין והסטטוס היו קיימים במסד ולא הייתה שום דרך
לגעת בהם חוץ מ‑SQL Editor. עכשיו:

- **מצב המחזור** — פתוח / נעול / משחקים / הסתיים.
  זו הנעילה האמיתית: השרת בודק אותה **לפני** השעה, ולכן "נעול"
  חוסם הגשות מיד גם אם הדדליין לא הגיע.
- **דדליין** — נגזר אוטומטית מהמשחק המוקדם ביותר. שינוי ידני
  דורס את החישוב עד להזזת המשחק הבא.
- **שעות המשחקים** — הזזת משחק מזיזה את הדדליין איתו, אם הוא
  הפך למוקדם ביותר.

## 8. מה נבדק, ומה לא

**נבדק כאן, על PostgreSQL 16 אמיתי ובקוד:**

- 48 בדיקות SQL, על מסד ריק, פעמיים ברצף (אידמפוטנטיות).
- 251 בדיקות יחידה.
- `tsc --noEmit` נקי.
- רינדור מלא של האפליקציה ושל לוח הניהול בצד שרת.

הבדיקות החדשות (`db/tests/05_live_data.sql`) בנויות כ**מעגל
סגור**: כותבות דרך פונקציית אדמין, וקוראות דרך הפונקציה שהמסך
קורא לה. בדיקה שרק מוודאת שה‑UPDATE לא נפל הייתה עוברת גם
בגרסה השבורה.

**לא נבדק — ואי אפשר לבדוק מכאן:**

- `npm run build`. אין גישה ל‑registry מהסביבה הזו. זה החלק
  היחיד שאני מבקש שתריץ ותגיד לי אם נפל.
- ה‑Edge Functions, כניסת גוגל, וקישור חשבון אופסיידס.
- Realtime בפועל — הוא דורש Supabase חי.
