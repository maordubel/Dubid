## מה זה בעצם — סיפור האיחוד

היו שני קודים: **דוביד-web** (PWA מלוטש, מנוע ניקוד, מיתוג, כרטיסי
שיתוף — אבל עם סגל חלקי של 6 קבוצות בלבד) ו-**דוביד-5x5** (סגל מלא
של **14 קבוצות · 350 שחקנים** עם עמדות, עם מנגנון שמירה בשם + קוד
קסם — אבל בלי מנוע ניקוד עשיר ובלי המיתוג).

האיחוד: הבסיס הוא ה-PWA (הקוד, המיתוג, מנוע הניקוד, כרטיסי השיתוף
— לא נגעתי בהם), ולתוכו הוזרם **הסגל המלא** מ-5x5, מוצלב מול קובץ
הדירוגים העדכני שסיפקת (133/350 שחקנים עודכנו בדרג/שווי לפי הקובץ
החדש). זה בדיוק מה ש`resolveRules()` היה בנוי לחכות לו: ברגע שיש
14 קבוצות, **מצב ההדגמה נעלם מעצמו** וההרכב חוזר ל-11 שחקנים מלאים,
בלי שינוי קוד — זה בדיוק מה שקרה.

מעליהם נוספו שלושה חלקים חדשים כדי שהמוצר יהיה שלם למחזור אמיתי:

1. **`data/fixtures.ts`** — לוח מחזור 1 שסיפקת, ממופה לקבוצות. מוצג
   כרצועה בעמוד הבית ומעל בורר ההרכב, וגם *בתוך* גיליון בחירת השחקן
   ("נגד מי משחקים" ליד כל קבוצה) — כדי שהבחירה תיעשה מתוך ידיעה מי
   בכלל משחק השבוע.
2. **`components/AdminPanel.tsx`** (`/#admin`) — לוח ניהול אחורי: תוצאה
   סופית לכל משחק + דקות/שערים/בישולים/כרטיסים/שער-נקי לכל שחקן.
   זה בדיוק המקום שיוחלף בחיבור API כדורגל אמיתי — עד אז, זה מזין את
   אותו `scoreLineup()` בדיוק.
3. **`lib/store.ts` + `components/Leaderboard.tsx`** — "מסד נתונים"
   מבוסס `localStorage` (בלי שרת, כדי שהדמו יעבוד הערב): הרכבים
   נשמרים עם שם תצוגה + קוד קסם (`DB-XXXX`, בדיוק כמו ב-5x5
   המקורי), והדירוג מחשב אותם חי מול תוצאות המחזור שהאדמין הזין.

## מה נשאר לבדוק לפני שמראים את זה למישהו

* **קוד גישה לאדמין הוא `dubid2027`, קשיח בקוד** (`src/lib/store.ts`).
  מספיק כדי שאף אחד לא ייכנס בטעות ללוח הניהול הערב — **לא** אבטחה
  אמיתית. להחליף ב-auth אמיתי (יש כבר Supabase מחווט בפרויקט) לפני
  שהאתר נגיש לציבור.
* **`localStorage` = מסד הנתונים של ההדגמה.** הרכבים ותוצאות שמורים
  בדפדפן של כל מכשיר בנפרד — מעולה להדגמה על מסך אחד הערב, לא מספיק
  לכמה אנשים על מכשירים שונים. ה-Edge Function וה-DB schema כבר קיימים
  בפרויקט (`db/`, `supabase/functions/score-gameweek/`) בדיוק בשביל
  השלב הבא.
* **עירוני קרית שמונה: 0 חלוצים בסגל המקורי** (`scripts/squads.report.md`
  נוצר מחדש אוטומטית בכל הרצה של `npm run build:squads` ומדווח על זה).
  לא תיקנתי בניחוש — לא ברור אילו קשרים בפועל משחקים כחלוצים.
* **שני שמות שחקנים תוקנו בפועל** (לא רק דווחו): `P806`
  ו-`P809` הכילו אותיות ערביות שהתערבבו לתוך שם עברי (ככל הנראה
  הומוגליפים — ו/ר ערביים שנראים כמעט זהים לעבריים, ומילה ערבית
  שלמה "أبو" במקום "אבו"). תוקן ישירות במקור (`scripts/squads.source.json`).
* **`nameEn` של שחקנים הוא `"TBD"` בכוונה** — לא הייתה בידי תעתיק
  אנגלי אמין ל-350 שחקנים, והמצאה הייתה גרועה יותר משדה ריק מסומן.
  השדה לא מוצג היום בשום מקום ב-UI, אז זה לא משפיע על מה שרואים
  הערב — רק על עתיד (ייצוא/סנכרון API).
* **`npm install` / `npm run build` לא רצו בסביבה הזו** — אין גישה
  לרשת בסנדבוקס שבו נבנה הקוד. כל קובץ נבדק תחביר וטיפוסים דרך
  `tsc`/`esbuild` וכל 70 הטסטים רצו בהצלחה מקומית
  (`node --experimental-strip-types --test tests/*.test.ts`), אבל
  זה לא תחליף ל-`vite build` אמיתי — הריצו את זה לפני שאתם עולים.

## 1 · מנוע הניקוד — לפי המפרט שהוגדר

```ts
import { scoreLineup } from './lib/scoring/engine.ts';
import { IL_PREMIER } from './lib/scoring/rules.ts';

const score = scoreLineup(lineup, performances, outcomes, IL_PREMIER);
```

**רובד 1 — ציון אינדיבידואלי**

| פעולה | נקודות |
|---|---|
| שער — שוער / מגן | 6 |
| שער — קשר | 5 |
| שער — חלוץ | 4 |
| בישול | 3 |
| שער נקי (דורש 60 דקות) | 4 |
| כרטיס צהוב | ‎-1 |
| כרטיס אדום | ‎-3 |

**רובד 2 — בונוס קבוצתי אמיתי:** ניצחון `+4` · תיקו `+1` · הפסד `0`.
פר שחקן, לפי הקבוצה שהוא מייצג בהרכב.

**רובד 3 — שער ההרכב הווירטואלי:** סכימת שערי כל הקבוצות שבהרכב
לקופה אחת; כל 2 שערים = שער וירטואלי של `+5`. שאריות נשמרות ומופיעות
בפירוט (`meta.remainder`).

**רובד 4 — הקפטן הדובידי:** `×3`, חסינות לצהוב (60 דקות ומעלה + לא
הפסידו; אדום לא נסלח), והעברה אוטומטית לסגן אם הקפטן לא שיחק.
ציון שלילי לא מוכפל.

## 2 · אכיפת "שחקן אחד מכל קבוצה" — ארבע שכבות

| שכבה | מנגנון |
|---|---|
| **UI — מניעה** | רצועת "כיסוי קבוצות" מעל המגרש: 14 צ׳יפים, מלאים בכתום, ריקים באפור |
| **UI — הסבר** | בגיליון הבחירה שחקן מקבוצה תפוסה **מואפר + קו חוצה + ✕**, והכיתוב אומר בדיוק *מי* חוסם ומי היריבה השבוע: „מכבי חיפה · כבר בחרת את כיוף" / „מכבי חיפה · נגד הפועל רמת גן" |
| **שירות** | `validateLineup()` — קודי שגיאה מתורגמים he/en, נבדק לפני כל כתיבה ובתחילת כל חישוב ניקוד |
| **DB** | `UNIQUE (lineup_id, team_id)` + טריגר הגשה + `one_captain_per_lineup` |

## 3 · לוח הניהול (`/#admin`) והדירוג

זרימת העבודה עד שמתחבר API כדורגל:

1. נכנסים ל-`/#admin` (קישור עדין גם בתחתית עמוד הבית), מקוד גישה.
2. לכל משחק במחזור: תוצאה סופית (שער-שער), שמירה.
3. פותחים "הזנת שחקנים" למשחק — לכל אחת משתי הקבוצות מוצג הסגל שלה
   עם שדות מהירים: דקות (0/30/60/90), שערים, בישולים, צהוב, אדום,
   שער נקי. כל שינוי נשמר מיידית.
4. "פרסם דירוג" — ברגע שנלחץ, `Leaderboard` מחשב מיידית את כל
   ההרכבים שהוגשו דרך `scoreLineup()` ומציג טבלה מדורגת. אין המתנה
   לרענון, אין build נוסף — זה אותו קוד לקוח, אותם נתונים ב-`localStorage`.

## 4 · שמירת הרכב — שם + קוד קסם

בלי הרשמה: בסיום בניית ההרכב מוקפץ מודל לשם תצוגה, ונוצר קוד קסם
(`DB-XXXX`, אותו פורמט בדיוק כמו ב-5x5 המקורי) שמאפשר בעתיד לשחזר
את ההרכב ממכשיר אחר (`findEntry(name, code)` ב-`lib/store.ts` —
עדיין לא מחובר למסך UI ייעודי, קנדידט טבעי לתוספת הבאה).

## 6 · מובייל ו-RTL

**הניווט התחתון לא מסתיר תוכן** — גובה הניווט חשוף כמשתנה CSS
(`--nav-h`) ש-`AppShell` מוסיף כ-padding לאזור התוכן;
`env(safe-area-inset-bottom)` בתוך הגובה; ו-`100dvh` במקום `100vh`.
מעל `lg` אותם פריטים הופכים ל-`SideRail` אנכי + עמודת צד — אותן
קומפוננטות, לא שני מימושים.

**RTL:** אין `left`/`right`/`ml-`/`mr-` בשום קובץ — רק
`ps/pe/ms/me/start/end/border-s/border-e/text-start`. מספרים ב-`.num`
(`dir="ltr"` + `tabular-nums` + `unicode-bidi: isolate`), שמות לטיניים
בתוך עברית ב-`<bdi>`.

## 7 · מה אומת בפועל

```
npm test               →  70 tests, 70 pass
```

* **מנוע הניקוד — 31 טסטים.** כל ערך במפרט נבדק בנפרד, ובנוסף תרחיש
  מחזור מלא שחושב ביד: אישי 32 · תוצאה 23 · קפטן 25 · וירטואלי 35 = **115**.
* **מחולל ה-QR — 20 טסטים** בקריאה הפוכה: מסיר מסכה, קורא זיגזג, מפרק
  שזירה, מאמת Reed–Solomon, ומשחזר את המחרוזת.
* **קבצי הפריסה — 9 טסטים.**
* **הדאטה — 10 טסטים.** כל 14 הקבוצות קיימות, אין מזהים כפולים, לכל
  קבוצה יש שוער וסגל של 11+ שחקנים, ואפשר להרכיב הרכב מלא וחוקי של
  11 מהדאטה בפועל — **בלי מצב הדגמה**.
* כל קובץ חדש/שהשתנה נבדק גם דרך `esbuild`/`tsc` (תחביר + טיפוסים +
  שכל הייבואים בין הקבצים מסתדרים), כי `npm install` לא זמין בסביבת
  הבנייה עצמה.

### מה לא אומת

* `npm run build` (`vite build`) עצמו — הריצו אותו לפני עלייה.
* `navigator.share` עם קבצים — צריך מכשיר אמיתי (iOS Safari / Chrome אנדרואיד).
* ה-Edge Function לא הורץ מול פרויקט Supabase חי; `lib/store.ts` הוא
  תחליף מכוון ל-`localStorage` עד שזה יחובר.
